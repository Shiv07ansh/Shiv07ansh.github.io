How I built a voice-activated medicine reminder on a $4 microcontroller

The real story behind the paper: what the ESP32-S3 can actually do, why the first architectures failed, and what it took to get two neural networks running simultaneously in 330KB of RAM.

Lorem ipsum dolor sit amet, consectetur adipiscing elit. The problem I was trying to solve was simple to state: elderly patients miss doses because existing reminders are either too passive to notice or too complicated to interact with. The solution turned out to be anything but simple.

What I did not expect was that the hardest part would not be the machine learning. It would be fitting two trained neural networks into a microcontroller with less RAM than a floppy disk.

Why the ESP32-S3

I evaluated thirteen microcontrollers before settling on the ESP32-S3 Mini. The decision came down to three things that no other board in the sub-$10 range offered simultaneously.

Criterion Why it mattered ESP32-S3 answer
Local inference No cloud dependency allowed TFLite Micro compatible
PSRAM Tensor arenas exceed internal SRAM Up to 4MB external PSRAM
Power 7+ day battery target 0.08mA deep sleep
WiFi Optional caregiver notifications Integrated, no extra module

The Arduino Nano scored best on power and cost but cannot run TFLite Micro at all. The Raspberry Pi could run anything I threw at it but drew 650mA and cost $55. The ESP32-S3 was the only device without a critical weakness in any dimension that mattered.

The cascading inference architecture

The key architectural insight was that you do not need one model to do everything. You need two models that each do one thing well.

The KWS model runs continuously at ~30ms per inference, listening for any medicine-related command. Only when it fires does the SLU model activate. This mirrors exactly how Alexa and Siri work at commercial scale, but running entirely on a $4 chip with no internet connection.

The KWS model is a 2D CNN operating on MFE spectrogram features. It sees 49 frames of 40 mel filterbank values and outputs a binary classification: medicine-related command or noise. It occupies 130KB of SRAM and runs in about 30ms.

The SLU model is architecturally completely different. It operates on tokenized text, not audio features. Once KWS fires, the captured audio is transcribed and fed as a token sequence of length 15 into an Embedding layer, then GlobalAveragePooling, then a Dense classifier over 8 intent classes.

Three things that did not work

Bidirectional LSTM

My first SLU architecture used a bidirectional LSTM which gave noticeably better validation accuracy. It deployed fine to a TFLite file. It failed completely on device. TFLite Micro does not include the ReverseV2 kernel that bidirectional layers require. The error at runtime was an op-resolution failure with no clear message. I spent two days on this before finding the cause buried in a GitHub issue from 2021.

The fix was straightforward once identified: replace bidirectional with stacked unidirectional layers. Accuracy dropped by less than 1%. The lesson was not to assume that a model that converts to TFLite will actually run on TFLite Micro. They are different runtimes with different op support.

AllOpsResolver

The first time I tried to load both models simultaneously the device rebooted immediately. The cause was AllOpsResolver, which loads every operator TFLite Micro knows about into memory, including all the backpropagation operators used for training. On a device with 320KB of usable SRAM this is immediately fatal.

// This causes SRAM overflow — do not use
tflite::AllOpsResolver resolver;

// Use this instead — register only what your model needs
tflite::MicroMutableOpResolver<8> resolver;
resolver.AddDepthwiseConv2D();
resolver.AddConv2D();
resolver.AddMaxPool2D();
resolver.AddFullyConnected();
resolver.AddSoftmax();
resolver.AddReshape();

Switching to MicroMutableOpResolver and registering only the ops each model actually used saved approximately 40KB of SRAM. I identified which ops to register by reading the error codes thrown at runtime, not by inspecting the model in Netron.

The tensor arena

The tensor arena is a statically allocated block that TFLite Micro uses for all intermediate tensors during inference. Getting this wrong either wastes memory or causes a silent crash with no useful error message. There is no way to calculate the correct size analytically. The only method that works is empirical: start high, reduce by 1KB until it crashes, add 2KB margin back.

Both arenas are allocated in PSRAM, not internal SRAM, using EXT_RAM_BSS_ATTR. Without this the firmware stack overflows before inference even starts.

The three-factor confirmation problem

Voice confirmation alone is not sufficient for the target population. A cognitively impaired user may say yes without having taken their medicine. This is not a theoretical concern. It is the reason simple voice-only systems fail in this context.

The system requires three independent confirmations before logging a dose: the SLU must classify confirm_taken above a confidence threshold, the Hall effect sensor must detect the pillbox lid opening, and the ultrasonic sensor must detect hand presence inside the compartment. All three must occur in sequence within a five-second window.

This is the part of the paper I am most proud of. It is not clever machine learning. It is careful systems thinking about what a robust real-world solution actually requires.

What the numbers mean

The paper reports 96.4% KWS accuracy and 94.1% SLU accuracy. Both numbers are from controlled single-speaker evaluation. I want to be honest about what that means: the system works reliably on my voice and degrades on voices it has not seen. This is the primary open problem the work surfaces, not resolves.

Generalising keyword spotting and intent classification to unseen speakers, regional accents, and non-native pronunciations within the memory constraints of an MCU is the research question I want to pursue next. It is harder than it sounds.

The full implementation is on GitHub at Shiv07ansh/AIoT-Medicine-Reminder including the training decisions log, hardware setup documentation, and every engineering challenge and workaround encountered. The paper is available as a preprint at zenodo.org/records/19034554.
